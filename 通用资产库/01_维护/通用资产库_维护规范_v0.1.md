# 通用资产库｜维护规范 v0.1

> [!summary]
> 目标不是让通用库越来越大，而是让它成为**越来越稳定、越来越容易被不同 World Pack 组合复用的机制资产层**。

---

# 1. 新资产先分类

任何新想法先判断：

## Core

拥有一个跨世界长期 Canonical Domain。

例如：

- Character Capability；
- Health；
- Combat；
- Relationship；
- Spell Magic；
- Divine。

## Gameplay

在已有 Core 上形成通用玩法闭环。

例如：

- Survival；
- Traveler/System。

## Theme

依赖已有 Core，对一个领域做深。

例如：

- Combat Magic。

## World-specific

核心机制离不开具体时代 / 地理 /组织 /历史事实。

这种资产：

> 不进入通用库。

---

# 2. Core 优先原则

如果发现：

```text
多个 World-specific / Theme Expansion
都需要同一套底层机制
```

应停止继续复制专用包。

先问：

> 是否缺少一个 Generic Core？

顺序：

```text
Generic Core
↓
Generic Downstream / Theme
↓
World-specific Expansion
```

这是当前通用库最重要的生产纪律。

---

# 3. Owner 先于内容量

判断是否值得新建资产的第一问题不是：

> “这个包能写多少内容？”

而是：

> **“它拥有哪个其他资产不应该拥有的 Canonical Domain？”**

无法回答：

> 优先作为现有资产的 Contribution / Theme / Module，而不是新 Core。

---

# 4. 关系必须类型化

禁止：

```text
dependencies:
  - everything
```

必须明确：

- Hard Dependency；
- Optional Integration；
- Module Conditional Dependency；
- Provider → Consumer；
- Handoff；
- Contribution。

---

# 5. 不允许 World Consumer 反向污染通用资产

某个世界第一次使用资产时，可以提供：

- World-specific Examples；
- Compatibility Notes；
- Reference Consumer。

不能把：

- 世界组织名；
- 世界人物；
- 世界历史；
- 世界神名；
- 世界地理；

写进 Generic Core 的 Canonical Mechanism。

---

# 6. 首发世界 ≠ Asset Family Owner

如果一个通用资产从某世界开发过程中诞生：

正确：

```text
Generic Asset
reference_world_consumers:
  - World A
```

不推荐长期：

```text
asset_family:
  World A / Generic Maybe
```

世界蓝图负责：

> 组合与消费。

通用资产库蓝图负责：

> 资产自身身份和依赖。

---

# 7. 下游影响审核

修改 P0 / P1 Core 时，必须列出所有已知消费者。

例如 Character Core 更新：

至少检查：

- Health；
- Combat；
- Magic；
- Divine；
- Character Cards；
- World-specific Capability projections。

修改 Health：

至少检查：

- Survival；
- Combat Handoff；
- Magic / Divine healing；
- Traveler healing。

---

# 8. UI Surface 审核

新资产默认先问：

> 能不能贡献到已有 Surface？

只有真正形成长期独立工作空间时才 owns 一级 Extension Surface。

优先顺序：

```text
Core Surface Contribution
→ Entity Detail
→ Player Status / Detail
→ Contextual
→ Global Notice
→ Extension Surface
```

一级 Surface Owner 必须唯一。

---

# 9. Open Attempt Gate

任何通用机制不能通过：

- Skill；
- Class；
- Relationship stage；
- Authority；
- Resource；
- Capability；

在输入层删除玩家尝试。

这些只影响：

- 是否成立；
- 成功机会；
- Formal Effect；
- 风险；
- 后果。

---

# 10. Machine Binding 暂缓

当前通用资产库还是 Semantic Library。

直到 G9：

- 不伪造正式 JSON；
- 不冻结字段；
- 不制造临时 Schema 让 Runtime 被迫适配；
- 不让 Creator 自建第二 Validator。

---

# 11. 版本纪律

## Patch

只修：

- Ref；
- 名称；
- Dependency closure；
- UI Host wording；
- Related Notes；
- Metadata。

## Minor

增加重要机制，但 Owner 不变。

## Major Rewrite

Owner / Scope / topology 真正改变。

任何 Major Rewrite 都必须：

1. 列 supersedes；
2. 做迁移说明；
3. 检查全部消费者；
4. 更新通用蓝图；
5. 更新版本矩阵。

---

# 12. 库级收敛审核触发条件

出现以下任一情况，应做一次 Generic Library Convergence Audit：

- 新增一个 P0 Core；
- Core 拆分 / 合并；
- 连续新增 3 个以上通用资产；
- 一个资产从 World-specific 提升为 Generic；
- 依赖出现环；
- 两个资产争夺同一 Owner；
- 两个资产争夺同一 Surface；
- G8 Host Contract 更新；
- G9 asset-spec vNext 冻结；
- Creator 开始正式绑定。

# 13. 推荐目录结构

```text
通用资产库/
│
├─ 00_总蓝图/
│  ├─ 通用拓展包资产库总蓝图
│  ├─ 当前版本矩阵
│  └─ Dependency Graph
│
├─ 01_Core/
│  ├─ Character
│  ├─ Health
│  ├─ Combat
│  └─ Relationship
│
├─ 02_Gameplay/
│  ├─ Survival
│  └─ Traveler-System
│
├─ 03_Supernatural_Core/
│  ├─ Magic
│  └─ Divine
│
├─ 04_Themes/
│  └─ Combat-Magic
│
├─ 90_Audits/
└─ 99_Archive/
```

未来不要再按：

> “这个资产第一次在哪个世界里做出来”

决定永久目录。

---

# 14. 每次维护结束必须更新

- 当前版本矩阵；
- Owner Registry；
- Dependency Graph；
- Consumer Matrix；
- Future Slot；
- Superseded / Archived；
- G9 Requirements Corpus（若产生新 Host 需求）。

---

# 15. 最终维护原则

> **先维护通用机制，再让世界去消费它；不要再让某个世界项目临时拥有一套本可通用的底层引擎。**
