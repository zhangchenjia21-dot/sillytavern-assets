# 通用拓展包资产库总蓝图 v0.2

> [!abstract] 资产库定位
> 本文件不是某一个 World Pack 的资产组合蓝图，而是**所有跨世界可复用 Expansion Pack 的库级维护基线**。
>
> 它回答：
>
> - 当前有哪些通用资产；
> - 哪些是上游核心、哪些是下游玩法 / Theme；
> - 谁拥有哪个 Canonical Domain；
> - 依赖怎样组织；
> - 哪些资产已经进入稳定通用基线；
> - 哪些仍是通用候选；
> - 新通用资产以后怎样加入；
> - 某个世界如何“消费”通用资产，而不反过来拥有通用资产。

---

# 1. 顶层原则

## 1.1 通用资产库不是 World Pack

通用资产：

> 描述可跨多个世界复用的机制语义。

World Pack：

> 决定某个具体世界为什么存在这些机制、如何解释它们、有哪些世界事实与文化表现。

因此：

```text
Generic Expansion
!=
World Pack
```

世界可以消费通用资产，但不能把通用资产重新变成自己的专用附件。

---

## 1.2 通用资产必须保持独立资产身份

即使某资产最初在某个世界项目中诞生，只要它已经通过跨世界可复用性审核，就应拥有独立的：

- Identity；
- Version；
- Owner；
- Dependency；
- Status；
- Changelog；
- Reference World Consumer。

不得长期把某一个 World Pack 蓝图当作它唯一的资产族身份。

---

## 1.3 Runtime 是最终执行权威

所有通用 Expansion 仍只描述：

- State / Resource / Condition；
- Rule；
- Action / Intent；
- Resolution semantics；
- Event / Handoff；
- Permission；
- UI Contribution；
- Host Requirement。

它们不得拥有：

- RNG；
- Dice；
- Program Judge；
- Formal Outcome；
- Atomic Commit；
- Game State 写入权；
- 任意前端代码执行权。

# 5. 关系类型

通用库只使用以下正式语义关系。

## 5.1 Hard Dependency

没有上游就无法保持当前资产语义。

示例：

```text
Health → Character Core
Combat → Character Core
Survival → Health
Magic → Character Core
Combat Magic → Character + Magic + Combat
Divine → Character Core
```

---

## 5.2 Optional Integration

双方可以独立运行，组合后增强。

示例：

```text
Combat ↔ Magic
Combat ↔ Divine
Health ↔ Magic
Health ↔ Divine
Relationship ↔ Combat
Relationship ↔ Survival
```

---

## 5.3 Module Conditional Dependency

整个包不依赖某 Domain，但启用某 Module 时必须存在目标 Owner。

主要用于：

> Traveler / System。

---

## 5.4 Provider → Consumer

上游提供正式语义 / Capability，消费者只读取。

例如：

```text
Character Core → Health
Character Core → Combat
Character Core → Magic
```

---

## 5.5 Handoff

只传：

- Cause；
- Event；
- Candidate；
- Effect；
- Context。

不转移 Ownership。

例如：

```text
Combat Physical Impact → Health
Survival Need Deficit → Health
Magic Backlash → Health
External Event → Relationship Interpretation
```

---

## 5.6 Contribution

资产向已有 Registry / Surface / Grammar 增加声明式内容。

例如：

```text
Combat → Character Skill Registry contributes martial skills
Magic → Character Skill Registry contributes magic skills
Combat Magic → Magic Spell Grammar contributes theme spells
```

# 6. UI Host 组织原则

通用资产库不按“一个 Expansion 一个一级栏目”组织。

当前建议：

## 不拥有一级 Extension Surface

- EP-CHAR-CORE；
- EP-HEALTH-CORE；
- EP-SURVIVAL；
- EP-COMBAT-CORE；
- EP-RELATIONSHIP-ROMANCE-CORE；
- EP-MAGIC-COMBAT。

它们优先贡献：

- Player Status；
- Player Character Detail；
- Person / Item / Place Detail；
- Core `人物 / 地图 / 物品 / 信息 / 目标`；
- Narrative Contextual；
- Global Notice。

## 可以拥有一级 Extension Surface

### EP-TRAVELER-SYSTEM

System ON 时：

> 建议 owns `系统`。

Traveler-only：

> 不创建独立 Traveler Surface。

### EP-MAGIC-CORE

长期法术工作空间成立时：

> 建议 owns `魔法`。

Theme Expansion：

> contributes `魔法`，不得重复 owns。

### EP-DIVINE-CORE

若当前游戏启用完整神契 / 神术玩法：

> 建议 owns `神术 / 信仰`。

具体最终 Surface ID 等待 G9。

# 7. 世界消费模型

通用资产库的资产不“属于”某个 World Pack。

正确关系：

```text
Generic Asset Library
↓

```

例如：

## 汉末三国

当前消费：

- Character Core；
- Health；
- Survival；
- Combat；
- Relationship；
- Traveler/System。

默认不消费：

- Magic；
- Divine；
- Combat Magic。

## 诸界余辉

已知首发消费：

- Character Core；
- Health；

- Magic；
- Combat Magic；

其他通用玩法可按世界组合决定是否启用。

# 8. 通用资产入库 Gate

一个新 Expansion 只有同时满足以下条件，才进入通用资产库。

## G1｜Cross-world Identity

核心机制不能依赖某个具体：

- 国家；
- 神名；
- 历史事件；
- 世界地理；
- 世界专有组织；
- 世界专用资源名。

---

## G2｜Owner Gap / Extension Test

必须先回答：

> 它拥有一个真正新的 Canonical Domain，还是只是现有 Core 的 Theme / Downstream？

不得为了“做一个新包”就复制第二 Owner。

---

## G3｜Upstream-first

如果一个新机制依赖尚不存在的通用底座：

> 先生产通用底座，再生产下游 Theme。

不得再发生：

> 先做大量专用包，最后补 Core，然后全族返工。

---

## G4｜Typed Relations

所有跨资产关系必须归类：

- Hard；
- Optional；
- Conditional；
- Provider → Consumer；
- Handoff；
- Contribution。

禁止统一写成模糊 `dependency`。

---

## G5｜Open Attempt

技能、权限、关系阶段、职业、身份：

> 不能变成玩家输入白名单。

限制的是 Formal Effect，不是 Attempt。

---

## G6｜Program Authority

资产不能：

- 直接提交 Game State；
- 控制 RNG；
- 绕过 Program Judge；
- 用模型输出当正式 Outcome；
- 执行任意代码。

---

## G7｜Information Boundary

后台 Truth：

> 不等于 Player Knowledge。

UI Contribution 必须基于 player-safe Projection。

---

## G8｜Surface Ownership

需要一级 Surface 时：

> 明确 owns。

否则：

> contribute 已有 Surface / Context。

duplicate Owner：

> preflight incompatible。

---

## G9｜Definition / Instance

资产只保存 Definition。

运行变化：

> 只进入 Game State。

---

## G10｜Creator Authorability

机制应可被有限声明式 Primitive 表达。

如果必须依赖：

- arbitrary JS；
- arbitrary React；
- 自建 Runtime；
- 自建 RNG；

默认不能进入当前通用库正式层。

---

# 9. 通用资产版本治理

## Patch

适用于：

- stale reference；
- 名称更新；
- Related Notes；
- UI / Host requirement 说明闭环；
- 不改变 Canonical Owner 的接口修订。

例如：

```text
0.2 → 0.2.1
```

---

## Minor

适用于：

- 新增重要机制；
- 扩展合法状态；
- 新 Module；
- 新 Resolution / UI 能力；
- 但资产核心 Owner 不变。

例如：

```text
0.2 → 0.3
```

---

## Major / Major Rewrite

适用于：

- Owner 改变；
- Scope 大幅迁移；
- 包拆分 / 合并；
- 依赖拓扑变化；
- 旧语义被正式废止。

当前 Markdown 阶段可以继续使用 `0.x` 演进，但变更说明必须明确写：

> Major Rewrite。

# 12. 维护工作流

以后每次新增或更新一个通用资产：

```text
1. 读取通用资产库总蓝图
2. 判断 Core / Gameplay / Theme / Framework
3. Owner Gap Check
4. Dependency 类型化
5. 讨论关键产品问题
6. 用户裁定
7. 正式创作 / 修订
8. 单资产审核
9. 下游影响审核
10. 更新 Current Version Matrix
11. 更新 Dependency Graph
12. 更新 Consumer Matrix
13. 必要时做 Generic Library Convergence Audit
```

不能只更新单资产文件而忘记库级蓝图。
